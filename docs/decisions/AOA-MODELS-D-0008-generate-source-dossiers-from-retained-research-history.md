# Generate source dossiers from retained research history

## Status

Accepted for the owner-local experimental repository.

## Index metadata

- Decision ID: AOA-MODELS-D-0008
- Original date: 2026-09-04
- Owner facets: research-intake, source-history, currentness, generated-read-model
- Posture: accepted-owner-source

## Context

Repeated web reconnaissance now revisits some external pages across model
families, time windows, and questions. `ReconRun` source captures correctly
retain what each pass used, while capture snapshots, change receipts, and
supersession proposals retain narrower temporal and review history. A later
agent should be able to see that accumulated history before citing or
refreshing a source without scanning every packet or maintaining a private
dedup table.

Making a second authored dossier for every URL would duplicate titles,
publishers, segments, dates, and interpretation. Those copies would drift and
would make agents choose between two source records. Automatically fetching
every prior URL on every pass would instead turn a lookup need into a crawler
and falsely suggest that recency is equivalent to truth or usefulness.

A future contributor would lose why source dossiers are generated from
retained evidence, why their identity is intentionally conservative, and why
their currentness fields deny freshness if this boundary existed only in a
helper script.

## Options considered

- Keep cross-run source lookup manual by searching all recon packets and
  automation artifacts on every pass.
- Add one mutable, manually updated dossier file per external source alongside
  the existing source captures.
- Add a second append-only source-visit object and copy every `source_capture`
  into it.
- Build a crawler or scheduler that refreshes all known sources and computes a
  source rank or consensus automatically.
- Generate one deterministic, queryable source-history catalog from the
  retained `ReconRun` and research-automation records.

## Decision

Generate `generated/research-source-dossiers.json` as a pre-canon read model.
One dossier groups all retained appearances of one normalized exact URI and
joins their segments, observation references, capture snapshots, change
receipts, metadata variants, and supersession proposals.

Normalize only syntax that does not distinguish the retrieved source surface:
lowercase scheme and authority, supply `/` for an empty path, and remove the
fragment. Preserve path case, trailing slash, and query. Do not infer aliases
between different normalized URIs from titles, publishers, redirects, or
content similarity.

Agents query the catalog before reusing a source. A pass that changes a
retained recon run or automation artifact rebuilds the catalog; the normal
validator rejects missing or stale generated bytes. Rebuilding performs no
network access. A live segment refresh remains an explicit, bounded action only
when the current research question needs new currentness or change evidence.

The catalog records currentness posture and attention signals but always sets
`freshness_asserted=false`. Attention highlights repeated unanchored use,
incomplete repeated segment digests, metadata conflicts, capture gaps, change
review, or supersession review. It is not a quality score, consensus threshold,
or promotion queue.

## Rationale

The existing append-only records already contain the facts needed for a source
dossier. Derivation keeps one source of authorship while giving every agent a
fast shared entry point. Exact input refs and digests make staleness detectable;
deterministic generation makes review and rebuild cheap.

Conservative URI identity avoids silently merging distinct versions,
localized pages, API queries, or path semantics. Separating catalog rebuild
from live refresh keeps ordinary interaction fast and prevents an agent from
turning every lookup into network activity. Explicit freshness denial preserves
the distinction between the newest retained observation, current external
state, and accepted model knowledge.

## Consequences

- Repeated sources have one shared history view without a second manual ledger.
- New providers, model families, source classes, and URLs remain data rather
  than code branches.
- An edited retained input makes the generated catalog stale until rebuilt.
- Single-use mutable sources remain visible without flooding the attention
  view; repeat use or an actual review pressure raises a targeted signal.
- Equivalent content at different URIs remains separate until a reviewed
  identity mechanism is justified.
- The catalog can grow large enough to warrant a later indexed storage or
  pagination contour; that change must preserve deterministic identity and
  authority denial.
- Discovery, live refresh scheduling, crawling, ranking, consensus,
  interpretation, promotion, canonical model writes, proof, routing,
  activation, and acceptance remain outside this decision.

## Follow-up route

Use dossier queries during later model-family reconnaissance and observe real
lookup, alias, refresh, and review pressure. Add a reviewed alias relation only
if exact-URI separation repeatedly obstructs valid work. Consider indexed
storage only if measured catalog size or query latency warrants it. Scheduling,
discovery, ranking, consensus, and promotion each require separate owner
evidence and decisions.
